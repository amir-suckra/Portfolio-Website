BlockBreak

JavaScript p5.js Game Design User Testing

About the course

BlockBreak was my final project for AP Computer Science Principles. The course's capstone is the College Board Create performance task: each student designs and builds an original program that uses a list, a procedure with a parameter, and an algorithm that combines sequencing, selection, and iteration.

Project Goal

Goal: design and program an original interactive game in JavaScript that meets the AP Create task requirements, then improve it through real user testing until it is fair, challenging, and easy to read.

What I Built

BlockBreak is a block-breaking arcade game. You move a paddle with the arrow keys, or by dragging your finger on a phone, to bounce a ball into rows of orange blocks, earning a point for every block you break. You have three lives. Clearing every block moves you up a level, and each of the five levels adds another row of blocks and speeds up the ball. The game has a start screen, the game itself, and a win or game-over screen with a restart button, all run by a simple state machine.

Play It

Click or tap Start, then use the ← → arrow keys, or drag your finger on a phone. Turn your phone sideways for a bigger screen.

How It Works

The blocks are stored in a list. createBlocks() fills it with one object per block (position, size, and whether it is still visible), adding more rows at higher levels. The required procedure, BlocksAndScore(pointsPerBlock), runs every frame. It loops through the list (iteration), skips blocks that are already broken and checks whether the ball overlaps each remaining one (selection), then hides the block, bounces the ball, and adds points (sequencing):

function BlocksAndScore(pointsPerBlock) {
  for (let i = 0; i < blocks.length; i++) {
    let b = blocks[i];
    if (b.visible) {
      fill(255, 150, 0);
      rect(b.x, b.y, b.w, b.h);

      let ballLeft = ball.x - ball.r;
      let ballRight = ball.x + ball.r;
      let ballTop = ball.y - ball.r;
      let ballBottom = ball.y + ball.r;

      if (ballRight > b.x && ballLeft < b.x + b.w &&
          ballBottom > b.y && ballTop < b.y + b.h) {
        b.visible = false;
        ball.speedy *= -1;        // bounce the ball
        score += pointsPerBlock;
        break;                    // only one block per frame
      }
    }
  }
}

Build Process

  1. Plan the game. Defined the screens (start, game, end), the ball and paddle objects, and the list of blocks.
  2. Build the core loop. Paddle movement with the arrow keys, ball motion, wall and paddle bounces, scoring, and lives.
  3. Get collisions right. Compared the ball's edges, not just its center, against each block and the paddle so hits match what you see on screen.
  4. Test with real players. Had other people play the game, then kept a change log of their feedback and my fixes.
  5. Iterate on the feedback. Made the paddle faster, fixed the ball passing through blocks and a neighboring block disappearing on a hit, tightened the hitboxes, added five levels with rising difficulty, and darkened the background after one tester rated readability only a 3 out of 5.
  6. Make it work on phones. Added touch controls so the paddle follows your finger, and stopped the page from scrolling while you drag, so the game can be played on a phone as well as a computer.

My Role

This was an individual project. I designed the game and wrote the program. The start screen and the clickable-button helper are adapted from an earlier class project, and that is credited in the code comments.

Key Problem Solved

Collision bugs. At first the ball could pass straight through blocks, and sometimes a block next to the one that was hit would disappear too. Checking the ball's edges against each block's exact rectangle, and stopping after the first hit in each frame, made every hit register once and only once.

What I Learned

How games run as a loop of update and draw steps controlled by a state machine; collision detection; supporting both keyboard and touch input; organizing code into procedures with parameters and data into lists; and how much real user testing improves a program. My change log still has two ideas for the next version: power-ups and upgraded graphics.
